# Phase 9: Checkpoint revert

> Implemented via `feature/checkpoint-revert`.

## Context

Spec [#33](https://github.com/deanjstone/argusde/issues/33)'s Problem Statement names "checkpoint/rewind history" as one of the headline gaps versus T3 Code, and its Testing Decisions section explicitly says checkpoint git plumbing should support "capture/diff/**revert**" as a small, direct, testable module. Phases 1–8 built capture (turn-0 baseline + per-turn) and diff (`thread.diff-checkpoints`), but never revert — confirmed via a fresh repo survey: `CheckpointStore` has only `captureBaseline`/`captureCheckpoint`/`diffCheckpoints`, there's no `thread.revert-checkpoint`-style WS command, and no UI action for it anywhere. This is the last unimplemented piece of the checkpoint story and, unlike the other three remaining spec gaps (PWA installability, Thread close, resume-last-thread), it's the one explicitly named in the spec's own problem statement.

## Facts gathered this session (not assumed)

- **Checkpoint git plumbing** (`src/server/checkpoint/checkpoint-store.ts`, 73 lines): each checkpoint is a full parentless snapshot commit at `refs/argusde/checkpoints/<threadId>/turn/<n>`, built via an isolated `GIT_INDEX_FILE` so `captureCheckpoint`/`captureBaseline` never touch the real index. A revert is fundamentally different — it *must* mutate the real working tree — so it can't reuse that isolation; it needs `git read-tree -u --reset <ref>^{commit}` (or equivalent) against the real index/worktree, verified against a real temp repo during implementation, not assumed to work first try.
- **Turn numbering lives entirely in-memory on `ThreadRuntime`** (`private nextTurn = 1`, only ever read/mutated by `this.nextTurn++` inside the private `completeTurn()`). No setter exists. Rather than adding one (which would need `ThreadRuntime.start()`/constructor changes to skip re-baselining, per the `thread.promote-to-worktree` precedent's dispose/recreate pattern not fitting a mid-conversation revert), the cleaner design is: **revert never resets `nextTurn` — it captures the target checkpoint's content as a brand-new checkpoint at the current `nextTurn`, then increments it normally.** This matches the codebase's explicit append-only philosophy ("checkpoint history is durable in git refs independent of any working copy" — nothing is ever truncated or overwritten) and needs zero changes to how `nextTurn` is managed.
- **`thread.promote-to-worktree`** (`ws-server.ts` lines 138–202) is the closest existing precedent for a mutating, guarded, event-appending command: `requireThread`, a domain-state guard, an event appended only after the mutation succeeds. Its in-flight-turn guard technique (checking `thread.message-recorded` events) answers "has any message ever been sent", which is the wrong question for revert (would block reverting entirely). Revert needs "is a turn *currently* in flight right now" — no existing field answers that.
- **`ClientCommandSchema`** (`ws-protocol.ts`): flat, uniform `{ type, commandId, ...payload }` zod objects in a `discriminatedUnion` — adding a command is a one-line addition, `ClientCommand` is auto-derived.
- **`thread.checkpoint-captured` projection** (`event-store.ts` line 74): `INSERT INTO checkpoints (thread_id, turn, ref, created_at)`, turn-0 alone uses `INSERT OR REPLACE` (re-baseline on worktree promotion), every other turn is a plain `INSERT` so a double-fire surfaces as a real error. `schema.ts`'s own doc comment confirms this project's accepted convention: "No migration framework — MVP-scale 'create if not exists' is sufficient" — so extending the `checkpoints` table with a new column is an accepted pattern here (a stale local dev DB just needs deleting), not something to work around.
- **In-flight-turn testing precedent**: `ws-server.test.ts`'s existing "refuses to promote a thread while a turn is still in flight" test builds a dedicated slow `agent()` whose `session.prompt` handler resolves only when the test manually calls a captured `releasePrompt()` — the standard `createFakeAgent` fixture resolves turns synchronously/fast, so this manual-release pattern is the only reliable way to create a real, controllable in-flight window. Reusable as-is for a revert-while-in-flight test.
- **UI attach points**: `checkpoint-strip.tsx` renders one button per turn (`onSelectTurn`); `diff-view.tsx` renders the diff for whatever `activeTurn` is currently selected, with only a "Close" button today. `App.tsx`'s `activeTurn` state already tracks "the turn whose diff is showing" for both `handleSelectTurn` (diff turn-1→turn) and `handleSinceStart` (diff 0→latest) — reverting to `activeTurn` is exactly "restore the working tree to how it looked right after that turn completed," the correct semantics in both cases.

## Design

**`src/server/checkpoint/checkpoint-store.ts`**: new method `restoreCheckpoint(threadId: string, turn: number, cwd: string): void`. Resolves `refFor(threadId, turn)`, verifies it exists via the existing `allowFailure` `git()` overload (throws a clear `Unknown checkpoint ref: <ref>` domain error if not, rather than leaking raw git stderr), then runs `git read-tree -u --reset <ref>^{commit}` against the real cwd/index (no `GIT_INDEX_FILE` override — this one has to touch the real working tree by design). Verify empirically against a real temp repo during implementation that this actually deletes files added since the target checkpoint and restores modified/deleted files, adjusting the exact plumbing (e.g. `git checkout <ref> -- .` + a explicit prune step) if `read-tree --reset -u` doesn't behave as expected on the git version in use.

**`src/server/persistence/schema.ts`**: add a nullable `reverted_to_turn INTEGER` column to the `checkpoints` table's `CREATE TABLE IF NOT EXISTS`.

**`src/server/persistence/event-store.ts`**: extend the `thread.checkpoint-captured` `DomainEvent` variant with an optional `revertedToTurn?: number` field (undefined for every existing/normal capture site, set only by revert). Update its projection's `INSERT` to include `reverted_to_turn` (`event.revertedToTurn ?? null`). Extend the shared `CheckpointRecord` interface (`ws-protocol.ts`) with `revertedToTurn: number | null`, and `listCheckpoints`'s SQL to select `reverted_to_turn AS revertedToTurn`.

**`src/server/session/thread-runtime.ts`**:
- New `private turnInFlight = false`, set `true` at the start of `sendMessage()` (right after persisting the user's `thread.message-recorded` event) and `false` at the start of `completeTurn()`. New `isTurnInFlight(): boolean` getter.
- New `async revertToCheckpoint(turn: number): Promise<{ newTurn: number }>`: throws if `this.turnInFlight`; calls `checkpointStore.restoreCheckpoint(threadId, turn, cwd)`; captures a new checkpoint at `this.nextTurn` via the existing `checkpointStore.captureCheckpoint`; appends a `thread.checkpoint-captured` event for that turn with `revertedToTurn: turn`; increments `this.nextTurn`; returns the new turn number. No ACP/agent-session interaction at all — this is pure git + persistence, safe to run without the agent being involved.

**`src/shared/ws-protocol.ts`**: new command `{ type: "thread.revert-checkpoint", commandId: string, threadId: string, turn: number }`.

**`src/server/ws/ws-server.ts`**: new `case "thread.revert-checkpoint"`: `requireThread`, validate the target turn exists via `eventStore.listCheckpoints(threadId).some(c => c.turn === command.turn)` (clear `Unknown checkpoint: turn <n>` error otherwise), look up the live runtime via `runtimes.get(command.threadId)` (always present — established precedent: runtimes are never deleted except at shutdown), call `runtime.revertToCheckpoint(command.turn)`, return `{ newTurn }`.

**Client (`src/web/`)**:
- `chat-state.ts`/component props need no changes — checkpoints already flow through `refreshCheckpoints`/`CheckpointRecord[]`, now carrying the new `revertedToTurn` field automatically once the shared type is extended.
- `checkpoint-strip.tsx`: show a small "↩" indicator on a turn's button when `checkpoint.revertedToTurn !== null` (title/aria-label naming which turn it reverted to) — cheap, uses data already flowing through once the type is extended.
- `diff-view.tsx`: new optional `onRevert?: () => void` prop; render a "Revert to this checkpoint" button next to "Close" in the header when provided.
- `App.tsx`: new `reverting` boolean state (mirrors `promoting`); new `handleRevertCheckpoint()` — guards `!client || !thread || activeTurn === undefined || reverting`, sends `thread.revert-checkpoint` with `{ threadId, turn: activeTurn }`, on success calls `refreshCheckpoints(thread.threadId)` and `handleCloseDiff()` (the pre-revert diff is now stale), on failure dispatches the existing `protocol-error` `chatStateReducer` case (matching `handlePromoteToWorktree`'s exact error-handling shape). Wire `onRevert={handleRevertCheckpoint}` into `ChatView`'s `<DiffView>` prop-through (same optional-prop-with-default pattern as `onSelectTurn`/`onSinceStart`).

## Explicitly deferred out of Phase 9

- PWA installability (manifest/service worker), Thread close + worktree auto-cleanup-on-close, and "resume most-recently-active-thread on reload" — separate, unrelated spec gaps identified during this session's survey; not part of checkpoint revert.
- Any confirmation dialog before reverting — matches the existing codebase convention (`handlePromoteToWorktree` also has no confirm step), and is lower-stakes here specifically because revert is non-destructive at the data layer: every checkpoint (including the pre-revert state) remains a durable, revertable git ref forever.
- Pruning/hiding "future" checkpoints after a revert — deliberately not done, matching the append-only design; the checkpoint strip just keeps growing forward, with the new "↩" badge marking revert points instead of hiding history.

## Testing (real collaborators over mocks, per established convention)

- `checkpoint-store.test.ts`: real-git tests for `restoreCheckpoint` — capture turn 0/1/2 with distinct file states between each (including a file added at turn 2 that didn't exist at turn 1), revert to turn 1, assert the working tree exactly matches turn 1's content (including that the turn-2-only file is gone) and `git status --porcelain` reflects the expected state; a second test asserts a clear domain error (not raw git stderr) for an unknown turn.
- `thread-runtime.test.ts`: a test using the standard `createFakeAgent` (deterministic/fast, per existing precedent) proving `revertToCheckpoint` mutates the workspace, captures a new checkpoint at the correct (continuing, not reset) turn number, marks it with `revertedToTurn`, and that `nextTurn` continues correctly for a subsequent normal `sendMessage`/turn afterward.
- `ws-server.test.ts`: a full protocol E2E test (create thread, two turns with real file changes via direct `fs.writeFileSync` between turns matching the existing checkpoint-diff test's pattern, revert to turn 1, confirm the new checkpoint appears via `thread.list-checkpoints` and the file content on disk matches); a rejection test for an unknown turn; and a rejection test for reverting while a turn is in flight, reusing the existing slow-agent/`releasePrompt` pattern verbatim.
- `diff-view.test.tsx`: new case(s) for the revert button — renders when `onRevert` is provided, calls it on click, absent when not provided (matching the existing optional-prop test pattern already used for `onClose`).
- `test/web-smoke.test.ts`: one new real E2E case — real server, real fixture agent, two turns with real file changes, click "Revert to this checkpoint" in the browser, confirm the file on disk actually reverted and the checkpoint strip shows the new reverted-marked turn.

## Outcome

Shipped as designed: `git read-tree -u --reset <ref>^{commit}` did the bulk of the working-tree restore, but empirically needed a follow-up `git clean -fd` — `read-tree` only reconciles paths that were already in the *real* index, and every checkpoint capture stages into an isolated `GIT_INDEX_FILE` (never the real one), so a file created after the target checkpoint is untracked from the real index's perspective the whole time and `read-tree` alone left it behind. Caught by the first real-git test run, fixed before it ever reached a higher layer.

Revert never truncates or resets anything, exactly as planned: `nextTurn` is never touched, the target checkpoint's content is captured forward as a brand-new turn marked `revertedToTurn`, and every prior checkpoint (including turns "after" the revert point) stays fully intact and diffable. The `turnInFlight` guard (set in `sendMessage`, cleared in `completeTurn`) blocks reverting mid-turn; tested by reusing `ws-server.test.ts`'s existing slow-agent/`releasePrompt` pattern verbatim, both at the `ThreadRuntime` unit level and the full protocol level.

The checkpoint strip's "↩ reverted to turn N" indicator is rendered as visible inline text, not a hover-only tooltip — deliberately, since the strip is mobile-first per spec #33's UI direction and hover tooltips don't work on touch. This surfaced a real test-selector trap during the web-smoke extension: a plain `text=/revert/i` wait, and even a role-scoped `getByRole("button", { name: /revert/i })` wait, both matched the *wrong* element (the badge text is nested inside its turn button's own accessible name) — settled on the diff panel's `aria-label` (`"Close diff"`), which is unambiguous. Worth remembering for any future UI text that reuses a word already used elsewhere in the page.

A second real bug was caught only by the manual E2E check against the real `claude-agent-acp`, not by any automated test: the manual server was importing a stale `dist/server` build (`pnpm run build:web` had been run repeatedly for other verification steps, but not the full `pnpm run build`, which also compiles the server's TypeScript) — the running server was several commits behind the source, and the checkpoint strip showed every turn as "reverted" nonsensically as a result. Not a real code defect, but a reminder that this repo's manual-check workflow needs a full `pnpm run build`, not just `build:web`, whenever server-side (not just UI) code changed since the last build.

Verification: full suite green (`pnpm run typecheck` + `xvfb-run -a pnpm test`, 206 tests across 24 files, including a new real E2E case), plus a real manual check against a live server and the real `claude-agent-acp` — two real agent-driven file edits, revert to the first, confirmed the second edit's content was actually gone from disk and the first's was intact, confirmed the new forward checkpoint's "reverted to turn 1" marker, then sent a further message afterward and confirmed it landed as Turn 4 with no numbering collision. `/code-review high` self-review completed before merge (see PR for findings/fixes, if any).

Deferred items (PWA installability, Thread close + worktree auto-cleanup, resume-last-active-thread, any confirmation dialog before reverting, pruning/hiding future checkpoints) remain out of scope, unchanged from the plan above.
